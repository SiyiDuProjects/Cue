# Sage / Sites 实际托管验证

验证时间：2026-09-30（洛杉矶）；结果文件为 UTC 2026-10-01。

## 结论

**当前普通 Sites Worker 请求不能作为 Sage 唯一的可靠任务执行后端。**
保持客户端连接的长流能完成；客户端断开后，任务在约 30 秒宽限期后被终止。
立即返回 HTTP 响应、仅用 `ctx.waitUntil` 执行的任务，也未完成。
这不是证明 Sites 永远做不到，而是明确否定“把长任务放在普通请求里就能稳定运行”的实现。
在持久任务执行、故障恢复和真实模型测试通过前，建议保留独立实时后端。
Sites 可承担网页、资料入口及 MCP；若只重视可靠结果，不应为了统一平台而提前撤掉执行后端。

## 测试边界

- 独立、仅本人可访问的站点：https://sage-runtime-validation.dusiyi0916.chatgpt.site
- 只使用合成 PCM、合成转录、随机 PNG 和合成生成任务。
- 没有使用麦克风、个人文件、真实面试内容、OpenAI API 密钥或付费模型。
- 没有修改、部署或重启正式 Sage。这里不是已经迁移好的产品。
- MCP 和主站入口采用平台访问控制；服务测试凭证仅通过隐藏标准输入传递，不保存到源码或证据文件。

## 对产品的影响

如果手机发起的普通流式请求是唯一任务宿主，切后台导致连接断开后，仍在运行的生成可能中断。
把状态写进数据库只能保存已经收到的片段，不能让已经终止的执行自动继续。
原型中的 running 残留也说明还需要执行租约、终态核对和明确的中断提示。

可继续研究的方案包括独立持久任务服务，或供应商支持的后台生成加断点读取。
本轮没有验证这些替代方案的真实延迟、工具调用循环、取消计费及恢复语义，不将其视为已经解决。

Cloudflare 的公开规则与实测吻合：HTTP 连接结束后，`waitUntil` 最多延长约 30 秒。
参考：https://developers.cloudflare.com/workers/platform/limits/#duration
