# Sage 产品方向：为能独立面试的人提供帮助

研究日期：2026-09-28。本文是产品决策记录，不是实现或上线报告。本轮没有修改运行代码、部署服务、启动音频采集或进行真实模型链路测试。

用户的核心约束：**“我不是傻子，我不用每句话都让 AI 告诉我。”**

目标不是让 AI 一直输出，而是减少查找、回忆、推演和实现时的负担；用户能自己推进时，工具应允许他不看、不点、不管理模型。

## 产品定案

**默认持续跟进，选择性提供简短而实质的参考；需要设计或实现时交付完整的工作区成果。** 不做逐句代答，也不退回每轮手动启动。

架构默认采用：**Live 负责现场理解与委派，现有托管 Sol 直接输出左侧文字，并通过工具更新右侧。** 不再把 Live 的语音字幕当作正式辅助答案，不再要求 Sol 的结论经过 Live 转述。暂不迁移 Realtime，不新增 Luna，也不为了这次改动重建独立后台链路。

这是一项职责与显示路径选择，**不是已经解决延迟的结论**。Sol 首段推理慢的问题仍要测量、优化；当前 high 只是比较基线，不是最终交互档位的承诺。

### 自动帮助的规则

判断的是：**现场是否出现尚未被当前对话和已有成果覆盖的实质信息需求，或明确需要交付的成果。** 不判断“用户是不是不会”，也不以每个问号、每次停顿为单位。

| 现场情况 | 默认结果 |
| --- | --- |
| 新题信息足够，需要确定方向 | 一次简短切入点；值得持续参考时写入分析，不倾倒整篇教程 |
| 新的知识问题或实质新取舍 | 可以自动给直接结论和必要理由；同一题内也不排除有价值的帮助 |
| 已有内容覆盖的追问、确认、复述，或用户已讲清相同结论 | 安静，不换一种措辞再说一遍 |
| 对话明确要求开始实现或修改已确定的方案 | 直接交付相应代码步骤，不再要求按一次开始或确认 |
| 只是比较替代思路、尚未决定采用 | 比较理由和代价，不自动重建整份实现 |
| 新条件改变旧结论 | 针对受影响部分纠正；正在实现则更新必要 patch，不重新从头澄清 |
| 用户正常思考、打字、停顿 | 记录上下文；不因沉默时长自动救场 |
| 用户点“帮我”或输入要求 | 必须处理这个明确请求；不再等待自动委派判定 |

这些是模型的行为约定和回放验收标准，不是新增一个关键词分类器。“已覆盖”指现场已有可用答案，而不是模型资料里存在相关知识；新的“为什么”“举例”“比较一下”仍可能构成实质需求。“可以自动给参考”不意味着每次一定要输出；没有新增价值时允许不显示。已有任务正在处理相同需求时，不重复启动。

自动内容默认适合扫一眼：直接结论、关键事实、重要限制或选择依据。需要完整推导、可照读措辞、长代码时才展开。避免“你应该表现出领导力”“你可以先澄清”这类空泛教学，直接给当前缺失的具体内容。行为题优先提供真实经历和事实线索，不默认写第一人称平行稿。

### 两个区域的交付约定

**左侧：眼前需要的帮助。** 简短知识解释、思路切入点、关键纠正、针对已选内容的追问都在这里。状态由应用显示，不写成答案。已完成内容继续追加保存，不偷偷改旧回答。

**右侧：本题可持续使用的成果。** 算法分析、OOD 职责和接口、系统设计取舍、图示关系、实现步骤均可进入。没有代码也可以有分析；没有持久参考价值则不必更新。

明确实现要求必须得到实现成果或具体阻塞原因，不能只说“开始实现”。明确工作区操作结束前，应用核对是否有成功提交、确实无需变更的结论或明确失败；普通文本响应结束不等于工作区完成。实际代码不可见时先按需取证，不能为完成任务编造外部文件；允许新建建议文件，但不能冒充已观察的实际文件。

分析和步骤独立更新，未更新不等于清空；改变方法时核对两者一致性。不强制统一 JSON，不删除正常工具续写，也不为左右各重新解一次题。

### 界面与按钮

1. **全局“帮我”**：针对当前未解决请求给实质帮助，支持快捷键；有明确的实现/设计要求时同时交付工作区。选中某段内容时明确针对该内容。
2. **右侧“更新工作区”**：固定针对本题工作成果，根据当前对话目标与实际代码更新。它不会因为用户恰好在分析或代码页签就偷偷改变意义。已有实现目标时重建剩余修改，讨论目标则更新分析；无需变化的部分保留。浏览历史也不把更新目标切到旧版，只有“沿用此方案”明确引用它。
3. **截图**：收集当前授权来源材料，显示缩略图；拍照本身不启动解题。帮助任务确实需要当前画面时可直接按需采集，避免让用户先截图再点帮助两次。
4. **换题、更多、结束**：沿用简洁主操作。更多容纳补充要求、换种解法、前题/往场记录、输入来源等；结束始终可见。
5. **暂停辅助**：停止自动帮助及其待发布结果，继续保留上下文；显式求助只授权本次，不隐式恢复自动辅助。真正结束才关闭本场。
6. **工作区内部**：步骤目录、完整代码、复杂度、复制、历史以及每步的修改/拆分保留在所属位置。不为“分析、回答、代码思考”添加模式选择器。

“帮我”与“更新工作区”是两个不同操作对象，不是让用户选模型。若用户尚未在对话表达实现意图却想直接要代码，可在同一个补充要求入口说“直接实现”；不增加强制阶段确认，也不承诺无信息按钮能读心。

不新增主文字区的题号、问答卡片或任务标题，不用弹窗追着用户确认。输入健康、失败、处理中采用简短应用状态；失败保留内容和草稿，在原操作处重试。

### 更新不打断阅读

首次工作区成果正常显示。用户主动更新/换解法后转到第一个修改；修改此步和拆步仍定位目标位置。仅更新分析或复杂度不改变页签、步骤和滚动。

自动产生的新版本可保存为当前方案，但用户已选定阅读的版本保持稳定，旁边出现一个“有更新／查看新版”入口。未被影响的内容无需冻结或提示。不要排出多个待批准版本；现有同题历史已足够承接中间版本。

如果正在看的建议已被明确判定失效，即使不自动跳页也要就近标明受影响原因，避免“阅读稳定”变成“继续展示过时建议而不告知”。这项有效性标记需要新增明确的数据语义，不能仅由前端看到时间戳更新就猜测。

### 截图、实际代码与历史

默认不持续截图或识图，不增加观察模型。保留手动收集及任务中的按需截图。读取原图是正常路径，不能把先 OCR 作为 Sol 的必经关卡。

实际代码是最近一次观察，不是始终同步的镜像；显示时间与局部覆盖。生成依赖当前实现的 patch 时先拿足够的新证据，同一文件屏幕外内容不编造。没有屏幕题面时可以依据口述；纯图片题可以只产出分析。

同题换变量、局部改法、算法替换、朴素到优化都基于当前实际代码更新剩余步骤。复杂度属于完成所选步骤后的整体实现。第一步就是第一次修改及 diff，不恢复“当前代码”编号页，也不恢复自动完成状态。

同题历史保留短摘要，如“朴素遍历”“哈希优化”。浏览是只读；沿用旧方法仍从当前实际代码重建。上一题是独立题目历史，不能与同题版本合成一个含糊的“上一步”。

只凭画面变化不自动清空换题。明确口头换题值得识别，但当前缺少可执行的自动题目切换接口；在接入前不宣称已经自动隔离。手动换题仍是确定性的纠正入口。自动切题若实现，必须复用同一归档和失效操作，不能另维护一份模型认为的当前题。

## 三段实际使用过程

### OOD：进程内任务调度器

| 现场 | Sage 的交付 | 操作 |
| --- | --- | --- |
| “设计任务调度器，先讨论；支持一次性与周期任务，不持久化。” | 分析记录已知约束，简短指出任务定义、调度状态、执行器的职责边界；不重问已给条件，不写实现 | 无 |
| 用户问“慢任务能否重叠”，得到“不允许” | 保存条件；用户正顺利处理时不追加左侧复述，不每句重写整页 | 无 |
| 用户决定将调度与执行分开 | 后续沿用这个方向；值得保存的接口/取舍更新分析，不另创一套框架 | 无 |
| 面试官问职责分离的理由 | 已有分析/候选人解释覆盖则安静；出现新的重要取舍时给简短增量，不重写实现 | 自动不足时点“帮我” |
| 用户自己解释清楚 | 不表扬、不生成同义答案，也不把助手先前建议当成用户说过 | 无 |
| “现在实现 add、cancel、run_due。” | 按需看实际代码，交付这三个接口的剩余步骤与 diff；左侧只点出关键实现考虑 | 无 |
| 新增多线程提交/取消要求 | 复核共享状态和取消边界，指出旧建议受影响之处；当前实现范围内更新 patch | 无；误解时一句纠正 |

OOD 指导放在后台的内容规则中：利用已知要求、只澄清真正改变设计的未知、根据对话推进职责/接口/实现。不是应用维护“第几阶段”，也不是每次重新输出完整 OOD 流程。

### 行为题

“讲一次团队意见冲突”：有可靠经历时给一次具体材料线索和关键个人动作，不默认写全文脚本。用户开始讲时不持续生成平行稿。后续新问题只补缺失事实或角度；用户明确要求润色时再组织完整措辞。资料缺少数字就不造数字，一般不需要右侧代码或方案。

### 算法：朴素解到优化

用户选朴素法，工具沿用；进入实现时生成朴素法的剩余修改。面试官问优化时先解释瓶颈与可选方向；明确采用哈希后，从当前实际代码给 patch，同题历史新增“哈希优化”。如果用户自己已经确定哈希法，直接跟进，不再教一遍如何想到哈希。仅问复杂度不自动换算法，也不为显示高效而跳过用户当前选择。

## 后台改动范围与风险

1. **接通后台的面向用户文字流。** 在现有 `response.event` 路径处理输出文字及生命周期；以真实委派/响应关系绑定任务，工具参数和推理事件不显示。不再发布 Live 辅助字幕。不是删除所有语音能力：模拟面试官的语音仍有独立用途。
2. **重写职责提示，不再修补口头转述。** Live 负责选择性委派，不自行答完重要请求后让左侧空白。Sol 的普通文字改为直接对用户有用的内容；工具负责持久成果，完成后只补必要信息。删除非代码不能用工作区的限制。
3. **明确操作交付状态。** 复用现有 operation/task 记录，区分文字答复完成、工作区成功、无需变更、缺材料和失败。对明确工作区请求核对实际提交结果，不用一句“已完成”作成功依据。
4. **分开当前成果与阅读对象。** 复用已有版本历史；自动更新不能重挂载、抢阅读。显式操作定位与自动结果提示由 UI 决定，不靠提示词。
5. **补足过期建议的语义。** 当前手动取消、换题、文件版本检查可以确定性阻止迟到写入；新语音并不自动取消。后续要使“新条件使旧建议失效”可执行，需由同一 Sol 读取上下文后报告目标、具体替代关系与依据版本，引用应用提供的 ID，由应用验证后执行。不能假设 native delegation 事件已经携带这些含义。报告应支持纯文字任务且不必等完整代码生成；不以空方案发布冒充控制操作。失效只影响对应目标，回答了一个追问不等于同题实现也已完成。这是待实现的协议能力，不是现有保证，也不是增加一个语义分类模型。
6. **长推理中的新信息边界必须诚实。** 收到新语音不等于正在生成的 Sol 已使用它。在重新接收/读取材料并复核前，无法保证立即停掉语义过时的文字。保留记录，及时追加纠正；不靠每个新转写都取消，亦不靠旁路分类器来假装解决。已知输入版本变化可显示“有新信息，待核对”，不能直接断言旧内容错误。
7. **按需观察与请求共用上下文。** 显式按钮可直接启动现有后台能力，不必须等 Live 再委派。仍区分原话、助手建议、实际代码和原图；无须增加 RAG 或阶段调度器。
8. **测量后调整后台交互配置。** 先辨明等待发生在哪里，保留 Sol 作为模型选择；推理档位是可调参数，不把 high 变成产品信条。没有数据前既不宣称必须换 Realtime，也不宣称现有链路已经够快。

不选择 Realtime 作为本轮默认，是因为它的工具调用/文字能力并非上述改动的必要前提；替换还会重做音频触发和后台上下文链。持续 ASR 加文字协调也合理，但需要重新承担语义触发、时序修正与上下文准备。当前先利用已存在的托管接入点；若回放证明 Live 委派是主要瓶颈，再换协调器，工作区和交付约定无需重做。

这不是为了少写代码而保留 Live，而是目前没有证据支持更换它能改善真正的问题。若证据相反，应删除或替换，不能因为已经做过就保留。

## 研究依据与当前事实

已在原有 [Pro 对话「面试辅助架构分工方案」](https://chatgpt.com/c/6ab9db4f-c09c-83ea-a089-aeee7b418892) 提交最新产品约束、现有实现和反例。Pro 的意见是外部评审；本文的取舍由 Codex 对照源码和用户需求作出。

已完成两轮讨论。第一轮给出整体默认方案；第二轮针对普通追问的漏答、过期任务的真实能力与速度承诺提出反例并收紧结论。没有逐条照抄：不采用“同题普通追问一概安静”，不新增主区域题号/标题，也不把模型意图理解包装成程序保证。完整原文保留在上述私有对话中。

本次源码核对发现：

1. `live_session.py` 收到 Live 字幕片段就发送给界面，没有人为逐字限速。约 1.2 秒空闲计时用于结束展示段落，并不用于延迟每个字。不能把慢直接归因于前端，也不能声称已证明服务端按真人语速限速。
2. 同一文件的 `backend_event()` 已关联托管后台任务、响应与工具，但没有将后台 `response.output_text.delta` 发布到左侧。改为后台文字直出具有现有接入点，不一定需要第三条应用侧 WebSocket。
3. `realtime_context.py` 已包含禁止 filler、重复播报、无请求实现等提示，但提示词存在不等于真实行为已通过验收。
4. 后台指令仍有 `Non-coding discussions need no workspace.`，与 OOD、系统设计需要持久分析的需求冲突，应修正“工作区只服务代码”的含义。
5. `code_workspace.py` 的显式生成路径已要求发布分析，并按实现需求交付步骤；可以为按钮设定交付要求，无需完全交给模型猜测用户点击的意义。
6. `workspace_actions.py` 已区分更新、修改、换解法、拆步和沿用历史。它们共享后台路径，而不是五个独立 agent。
7. 已有 `first_content_latency_ms` 从问题开始记录到展示段落开始，不能直接代表“问题说完到第一条有用帮助”的等待，也不足以区分委派、推理、工具、工作区发布及 Live 转述的耗时。
8. 本地修复、离线测试与生产行为是不同证据。本文没有重新验收已安装版本，也没有测出 Sol、Live、Realtime 的实际延迟排序。

官方接口核对：

- Live 托管后台会转发 Responses 文字事件；client delegation 则由应用准备上下文与执行后台请求。两者都不能被概括成“Live 完全不能触发应用工作”。[Live 委派文档](https://developers.openai.com/api/docs/guides/live-delegation)
- Realtime 支持函数调用及纯文字响应，但这些能力本身不能证明它在本项目更快，或更善于旁听两个人并判断何时介入。[Realtime 会话文档](https://developers.openai.com/api/docs/guides/realtime-conversations)

设计讨论必须分开三件事：**何时需要帮助、生成什么成果、如何稳定展示**。替换语音模型只改变其中一部分。

## 不应再退回去的产品边界

1. 熟练用户不是等待 AI 指挥的人。不要把每个停顿、每句追问、每次确认都变成完整答案。
2. “没有输出”可以是正确结果；但自动帮助失误后，用户必须有一个直接补救入口，不能必须先修理转写或调模型参数。
3. 不能判断用户脑中是否已经知道答案。介入依据应是对话里可观察的任务、请求、约束和已说出的内容，而不是推测用户能力或紧张程度。
4. 右侧是持久参考成果，不是代码专属容器。OOD 的对象职责、接口、约束与取舍同样值得留下；一句知识问答不必强行填满右侧。
5. 截图、实际代码、建议代码、候选人已经说过的话必须保持区别。看到了截图不等于要写代码，建议展示了也不等于用户照做了。
6. 一题只有一个当前工作区。更新和换解法都从已知实际代码继续；历史是可浏览的旧版，不是要用户管理的方案分支。
7. 自动生成不等于强迫阅读。新内容不得抢页签、拉滚动、覆盖用户正在看的版本；但已经失效的建议也不能继续冒充当前有效内容。
8. 不新增自动完成绿勾、阶段状态机、题型按钮、建议弹窗队列、独立 OCR/Luna 链路。持续截图默认不作为主流程依赖。

## 用来拷打方案的场景

这些是产品验收预期，不是已经执行的测试。

| 场景 | 正确行为 | 不可接受的行为 |
| --- | --- | --- |
| 面试官只说“嗯、对、继续” | 保留上下文，界面安静 | 新生成一段确认、总结或建议 |
| 用户正在清楚解释已确定方案 | 不复述、不评分、不补一段“你可以这样说” | 每个麦克风分段都引起辅助答案 |
| 真正的新设计题，条件尚不充分 | 只指出影响设计的关键未知；保留已知条件 | 从固定清单重问已经回答的所有问题 |
| 面试官明确要求实现刚才方案 | 基于实际代码交付步骤和 diff，不另问是否写代码 | 只说“下面开始实现”，右侧没有成果 |
| 普通知识追问，无持久成果需要 | 给足够直接的解释，工作区不强制更新 | 重写整份方案，或强行加代码页 |
| 用户想要工作区但自动链只出了文字 | 工作区操作明确要求交付分析或代码成果 | 按同一个模糊按钮反复碰运气 |
| 新约束使原方案无效 | 明确指出受影响条件，更新相应建议；保留历史 | 把更新前的代码继续标成当前适用 |
| 生成中用户已独立推进 | 使用最新可用事实，避免重复已完成内容 | 把数十秒前的起步建议当成现在的下一步 |
| 截图只显示文件局部 | 只更新确定片段，标明观察范围 | 用看见的半屏覆盖完整文件 |
| 口头已换题，屏幕还留旧题代码 | 新旧材料归属分开；不凭截图时间认领旧代码 | 旧题迟到结果写进新题工作区 |
| 用户正在看步骤，分析有更新 | 保持步骤和滚动位置 | 自动切回分析或第一步 |
| 没听清、连接断开、模型失败 | 显示真实状态，允许针对当前请求重试 | 用“好的/正在处理”掩盖失败或编造上下文 |

程序可以保证来源、任务身份、版本、原子提交、只读历史和阅读位置；它不能靠这些机制保证理解、算法、触发时机和截图识别永远正确。后者必须用真实场景检验，失败时提供短路径纠正。

## 最小验证，不做架构赛马

产品规则先确定，测试只用来证伪关键假设。先回放以下四组，每组覆盖正反例：

1. **顺畅讨论与真正追问**：熟练用户已完整解释时应安静；面试官提出新的关键取舍时应有帮助。检查漏掉有价值帮助与重复已说内容，而不是只统计少了多少条输出。
2. **OOD 从澄清到实现**：已回答条件不重问；设计讨论有持久分析；明确实现有步骤；解释已有代码不意外重写代码。
3. **朴素解到优化及生成中补条件**：优化从当前实际代码出发；复杂度跟随累积实现；新条件不能被迟到旧建议覆盖。
4. **手动补救、断线与阅读历史**：自动漏答后一击能补；明确工作区操作不能文字糊弄；旧任务、截图失败、历史查看不污染当前题。

需要分别记录：问题或请求信息充分的时刻、触发委派、后台开始、第一条有用文字、工具往返、完整工作区提交，以及实际显示时间。人工回放标注“有用”时刻；不要让“好的”“正在分析”获得低延迟分数。

如果主要慢在 Live 转述，后台文字直出应改善该段；主要慢在 Sol 推理，则再比较同一模型的推理档位；主要慢在完整步骤输出，则缩小当前实现范围，并先流式给有价值的结论。`max_output_tokens` 是上限，不是让模型必定生成相同长度，也不能靠调低它直接保证快速且完整。

只有自动触发持续失败时，才比较协调器替换。只改变一项后重放同一批材料，不同时换模型、提示词、调度和界面，再把任何变化都归功于新架构。

本轮没有执行以上真实调用。按项目约定，真实链路测试需要单独授权并使用 Luna；Luna 链路通过不等于 Sol 质量通过，付费 Sol/Astra 比较另需明确授权。
