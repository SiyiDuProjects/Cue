# Cue 0.4.1 build 22：原生音频输送修复

**build 22 已安装，用户在场短测未再出现缺口提示。** 云端仍为 Sites 版本 22，本次没有改动或重新部署云端，也未调用回答模型。

## 原因与修改

- 原生音频每路缓冲半秒，但输送定时器只在默认运行循环中执行；展开菜单、拖动及模态交互会暂停输送，采集线程仍继续写入，最终溢出。
- 输送之前只允许 `active` 阶段。原生启动和停止异步等待期间已经可能产生音频，因此慢启动、慢停止也可能填满缓冲。
- 定时器改为公共运行模式，直接在主线程回调中排出音频；上游准备好之后，在 `prepared`、`active`、`stopping` 阶段持续输送。采集缓冲在启动原生流前就发布，尾部仍先于停止标记发出。
- 保持原有半秒容量。真实阻塞导致的丢失仍报错，并区分麦克风和系统音频；本地诊断仅记录角色、阶段、丢失时长和输送间隔，不记录音频、转录或凭证。

## 验证与安装

- 控制实验将新测试中的输送策略恢复为旧实现：慢启动、慢停止、菜单跟踪和模态面板四项均能复现音频不完整。这是旧策略的受控复现，不是重新安装旧包进行录音。
- 离线检查通过：105 项原生检查、51 项音频输送断言、8 组 App Shot 上传预算夹具。音频检查使用真实编排与格式转换代码、合成 PCM 和模拟控制连接，不访问媒体设备、生产凭证或网络。
- 覆盖双路字节完整性及顺序、回答和停止之前的音频截止、取消启动后不能复活，以及真实阻塞仍必须报告缺口。
- Release 构建及签名验证通过；build 22 与 build 21 的指定签名条件相同。已替换 `/Applications/Cue.app`，build 21 回退副本和安装回执保存在忽略的 `artifacts/releases/20261009-cue-audio-build22/`。

## 钥匙串重复授权：已定位，未修复

用户同时报告每次更新后读取 “Sage Sites connection” 都要求登录钥匙串密码。只读检查当前连接条目的访问控制（未读取凭证内容）确认：应用信任列表之外，还有按 `cdhash:` 保存的 partition list，已积累 17 个程序指纹；build 22 的指纹已在本次授权后加入。

当前应用使用固定的自签名证书 `Cue Local Code Signing`，没有 Apple Team ID。指定签名条件稳定并不意味着 partition 身份稳定。Apple 的 [Security 源码](https://github.com/apple-oss-distributions/Security/blob/main/securityd/src/clientid.cpp) 中，符合 Apple 开发者证书链的应用按团队识别，其他已签名代码退回程序指纹；[Apple DTS](https://developer.apple.com/forums/thread/845980) 也确认信任列表与 partition list 是两项独立条件。因此，辅助功能授权已保留与钥匙串更新后仍询问并不矛盾。

默认钥匙串搜索列表目前没有可用的代码签名身份。持久修复应配置 Apple 签发的开发者身份，迁移旧凭证授权，并验证连续两次不同构建及重启后的读取。现有打包脚本支持 `CUE_SIGN_IDENTITY`。本次仅补充打包提示和文档，没有修改钥匙串访问控制、证书信任或已有凭证，不能宣称重复授权已解决。
