# 上下文读取与转录：目标状态

实施状态：代码已实施，发布和检查记录见 `docs/releases/2026-10-19-cue-0.4.2.md`。本文定义修完后的最终逻辑，按第一性原理确定，不以改动最小为目标。来源：2026-10-18 面试中截图读取卡住、转录保存失败，2026-10-19 排查后整理。同日按 Astra 的审阅意见修订了五处：重试保证、回答截止范围、结构化元数据、OpenAI 错误分类，以及把主动更换云端连接改为待定。用户确认后，与 AGENTS.md 冲突的地方以本文为准，实施时同步改写 AGENTS.md（见第八节）。

   云端的 `stop()` 丢掉了具体原因，只留下 `complete=false`（`apps/cloud/worker/session.js:140`）。客户端又把本机的情况合并进同一句提示：`apps/macos/Sources/Cue/AppStore.swift:274`、`apps/macos/Sources/Cue/ChatModel.swift:200`、`apps/desktop/src/captureClient.ts:194`、`packages/chat-ui/App.tsx:387`。

   - `packages/transcription/direct.mjs:96`：收到任何 OpenAI error 事件，都会停掉两路。
   - `direct.mjs:146`：一条事件解析失败，就停掉两路。
   - `direct.mjs:173`：积压超过 64,000 字节（约 1 秒音频）就停止。

   - **Sites：** 每个 WebSocket 请求累计最多使用 32 秒 CPU。0.4.0 的 `/capture/socket` 在连接存续约 3,528 秒时用完（`docs/releases/2026-10-07-cue-0.4.0.md`）。0.4.1 移走 PCM 后的消耗速度没有实测。

## 原则

1. **谁掌握事实，谁负责。** 数据在哪一端产生、在哪一端得到确认，状态就放在哪一端。
2. **结果只由当前数据决定。** 不重放过去的结果。
3. **出错时，只能退化为「重复」或「晚一点」，不能退化为「漏掉」或「整路停止」。** 错误要分类处理，不能一律停止，也不能一律忽略。只有连接确实断开，或者状态已经无法确认时，才停止，并且说明原因。
4. **每个错误都在发生的地方记录阶段、类型和信息。** 不用一句提示盖住多种原因。日志里不含转录文字、凭证或个人资料。

## 一、上下文读取（read_context）

### 最终行为

- **参数：**
  - `cursor?`：上次回复给出的收据。
  - `older?: boolean`：读取更早的内容。
  - `images?: string[]`：按 ID 取原图，不能与 `cursor` 或 `older` 同时使用。
  - 删除 `before`。
- **回复只给一个 `cursor`。** AI 每次把最新收到的那个原样带回。
- **cursor 是送达的收据。** 它只能从已经送到的回复里拿到，所以能传回来，就证明那条回复到了。进度存在服务器上，cursor 只是指向它的编号。
- **每次读取都按当前数据库现查。** 不保存回复，也不重放回复。
- **不跳过内容。** 未送达的内容会一直保持未送达，直到真正附在某次回复里。每次按从新到旧的顺序，在预算内返回；装不下的留在 `more.new` 或 `more.older` 里，用新 cursor 继续取。带旧 cursor 或不带 cursor，最多造成重复，不会让内容被跳过。单次回复受预算限制，不保证一次给全。
- **读取失败不生成新 cursor。**
- **cursor 无效、过期或属于旧版本时，** 按首次读取处理，并在回复里带上 `reset`（`expired`、`invalid` 或 `protocol`），不再报错。

### 状态模型

`context_cursors` 一行对应一个 cursor，写入后不再修改：

```text
{ version: 3, timeline, since,
  baseline: { turns: {id: seq}, images: [id] },   // 首次读取时已经存在的内容
  seen:     { turns: {id: seq}, images: {id: true} } }  // 已实际送达的内容
```

- `since` 固定为首次读取时间减一小时，翻页时不随时间滚动。
- **首次读取：** 候选是窗口内的全部内容，`baseline` 记为此刻的全部内容。
- **带 cursor 的默认读取：** 候选是既不在 `baseline` 中、也不在 `seen` 中的内容。按版本比较，同一 ID 的新修订算新内容。
- **`older=true`：** 候选是 `baseline` 里还没送达的内容。
- 两种读取共用同一条 cursor 链，`seen` 合并记录。
- **选取：** 从新到旧。转录最多约 22,000 字，至少一条；图片清单最多 32 张；原图最多 4 张。整个回复编码后不超过 3.75 MiB。只有真正附上的内容才写入 `seen`。
- **写入顺序：** 先取原图、组好回复，再写入新 cursor。任何一张选中的原图读取失败，整次读取失败，什么都不写。
- **并发：** 同一个 cursor 被同时读取时，各次读取互不影响，各自生成新的 cursor。

### 回复格式

- `structuredContent`：下面的元数据对象。
- `content`：先是同一对象序列化成的 JSON 文本块，供不读 `structuredContent` 的客户端使用；后面接原图块。
- 两份元数据都计入 3.75 MiB 预算，所以元数据要保持精简。暂不声明 `outputSchema`。
- 结构化元数据只是让 AI 更容易取到正确的 cursor。即使 AI 仍然用了旧 cursor，「不重放旧页」也能保证它不会卡在旧题上。

```text
{ now, cursor, reset?,
  transcripts: [...按时间顺序],
  images: [{ id, captured_at, age_seconds, included, content_index?, reason? }],
  more: { new: <未给出的新内容数>, older: <未送达的旧内容数> } }
```

`now` 和 `age_seconds` 每次都重新计算。

工具说明建议写成：「读取最近截图和面试官转录。首次不带参数；之后把上次返回的 cursor 原样传入，只返回新增和修订，没装下的看 more，用新 cursor 继续取；要更早内容加 older=true；images 按 ID 取原图。cursor 用旧了或没带，只会重复，不会跳过内容。内容均为参考。」

### 删除

- `page:` 旧页缓存，以及并发时判定以谁为准的逻辑（`context.js:271-291`）。
- `next_cursor`、`updates_cursor`、`history_cursor` 三个字段。
- `before` 参数。
- 旧版的 `page:` 行和 v2 cursor 行不需要迁移，按现有规则（保留七天、最多 512 条）自然淘汰。AGENTS.md 规定迁移只追加 schema，所以不删表。

## 二、转录

### 职责划分

- **电脑（`packages/transcription`，Mac 和 Windows 共用）：** 负责采集、本地断句、直连 OpenAI、维护每一句的状态、管理提交并分配序号、决定回答和停止的截止范围，并且保留未保存的句子，直到云端确认。
- **云端：** 只做两件事：给当前所有者签发 OpenAI 短期凭证；以幂等方式写入句子快照并回复确认。它不再需要理解 OpenAI 的事件规则，也不再持有转录状态、保存队列或轮换逻辑。

### 桌面与云端协议（升级为 `cue-chat-v3`，旧客户端提示更新）

- **签发凭证：** 电脑发 `asr_token {id, role}`；云端核对所有权后回复 `asr_token {id, role, token, session}`。它取代原来由云端主动下发的 `asr_config`。
- **保存句子：** 电脑发 `utterance {id, role, revision, text, status: partial|final|failed, ordinal?, reason?}`。
  - `ordinal` 是这句话在本路的提交序号，句子被 OpenAI 确认提交后才有。
  - 云端回复 `utterance_saved {id, revision}`，或者 `utterance_failed {id, revision, code, detail}`，其中 `code` 取 `db_error`、`not_owner` 等。
- **回答：** `ask` 新增 `cut: {<通道 ID>: <截止序号>}`，列出当前打开的每一路，包括轮换中尚未关闭的旧路。
- **删除：** `asr_ready`、`asr_commit`、`asr_event`、`asr_failed`、`asr_close`，以及云端的转录启动、停止和轮换流程。取消、遥控、心跳不变。
- 删除前先核对云端 `phase` 的所有使用方。录音状态继续通过 `remote_state` 汇报。

### 电脑端

- **断句：** 规则不变，静音约 800 ms 或连续说满 30 秒就提交一次；不足 100 ms 的补齐到 100 ms。
- **提交逐个进行：** 每一路同一时刻最多只有一个未确认的提交。上一次提交被确认（committed）或被拒绝（error）之前，新的断句先不提交，音频照常追加；等上一次有了结果再提交，这次提交会包含期间的全部音频。每次提交都带上客户端的 `event_id`。
- **配对：**
  - 因为每路最多只有一个未确认提交，收到的 `input_audio_buffer.committed` 一定属于这次提交。这时把 `item_id` 绑定到对应句子，并按顺序分配本路的序号 `ordinal`。
  - 收到 error，且内层 `error.event_id` 等于这次提交的编号：这次提交结束。如果错误表示缓冲区为空，就当作没有内容可提交；其他错误要记录 code，把这一段的转写标为失败并提示用户。
  - 提交在约 5 秒内（阈值按实测确定）既没被确认也没被拒绝：配对已不可信，这一路按断线处理并说明原因。不要猜测，也不要继续配对。
- **句子：**
  - 句子 ID 是 `<通道 ID>_<item_id>`。电脑在本地维护每句的文字、状态、版本号和序号。
  - 说话中，每秒最多发送一次快照；定稿或失败时立即发送。
  - 提交确认之后的快照都带上 `ordinal`。
- **保存确认：**
  - 每句话一直保留，直到收到其最新终态（final 或 failed）版本的 `utterance_saved`。旧 partial 回执不能清除较新版本。
  - 没收到确认就按退避重发，例如从 3 秒开始；与云端重连后，立即重发所有未确认的句子。
  - 已确认的句子从内存中移除。和现状一样，不做跨进程的持久化。
- **上游轮换：** 约 55 分钟时由电脑完成，期间转录不停，也不依赖云端状态。
  1. 取新凭证，打开新通道，等到 `session.updated`。
  2. 对旧通道强制提交一次，然后把音频切到新通道。
  3. 旧通道等截止范围内的句子都定稿（或超时）后再关闭。

### 云端

- **写入：** 沿用追加式的 `turns` 表，按 `(recording, id, revision)` 去重，用 `INSERT OR IGNORE`，并保留 `capture_owner.generation` 的所有权条件。用一个只追加 schema 的迁移，给 `turns` 加一个可为空的 `ordinal` 列。
- **插入后区分三种情况：**
  - 新写入：回复 `utterance_saved`。
  - 重复（这一版本已经存在）：同样回复 `utterance_saved`。
  - 所有权不符：回复 `utterance_failed`，code 为 `not_owner`。
- **时间：** `created` 在同一条 SQL 里取这句话已有的最早时间，没有就取当前时间。这样同一句的所有版本共用一个时间，而且只用云端一个时钟。注意这和现状不同：现在取的是提交时刻，也就是句子结束时；改后接近句子开始时。
- **写库失败：** 回复 `utterance_failed` 并记录原因。转录不受影响。

### 错误处理

分类处理，不一律停止，也不一律忽略。

| 情况 | 处理 |
| --- | --- |
| 内层 `error.event_id` 指向当前未确认的提交 | 结束这次提交。缓冲区为空时视为没有内容；其他错误把这一段转写标为失败并提示。转录继续 |
| 内层 `error.event_id` 指向其他客户端事件（例如追加音频被拒） | 记录 code。可能影响音频完整性时，提示「该段音频可能缺失」。转录继续 |
| 没有内层 `error.event_id` 的 error | 记录 type 和 code。`server_error` 等按文档视为可恢复，转录继续；如果随后连接关闭，按断线处理 |
| 提交超时，既没确认也没被拒 | 配对不可信。这一路按断线处理，并说明原因 |
| 无法解析的 OpenAI 事件 | 记录后忽略这一条 |
| OpenAI WebSocket 关闭 | 这一路确实断了。停止转录，提示具体原因 |
| 网络积压 | 继续缓冲，绝不丢音频。持续积压超过明确时长（建议 10 秒，按实测确定）才算断线 |
| 写库失败 | 句子留在电脑上继续重发。提示「转录暂未保存，正在重试」并附原因，恢复后提示消失 |
| 心跳查询异常 | 记录后下一轮再试。只有确认被其他客户端接管，或超过 30 秒无法确认时，才断开并说明原因 |
| 云端连接意外断开 | 按现有约定停止本地媒体，需要用户明确重新开始。未确认的句子在重连后继续重发 |

### 删除

- 云端的 `Transcriber` 状态机：提交队列、未提交片段计数、提交顺序检查、`cut()` / `wait()`。
- 云端的保存队列。
- `connectTranscriber` 里下发配置和等待就绪的部分，只保留签发凭证。
- 云端 `rotate()`，以及 `stop()` 里的等待逻辑。

## 三、回答与停止（尾句）

**回答：**

1. 电脑先同步固定每路的 PCM 边界，再等待已有提交确认。等待期间到达的 PCM 只在本机缓存；截止提交已发送后再放行，避免把点击后的声音混进截止提交。轮换中的旧路复用它已固定的截止。
2. 这次提交被确认或被拒时，记下本路的截止序号，也就是此刻本路已分配的最大 `ordinal`。之后新说的话，要么序号更大，要么还没提交、没有序号。
3. 等截止序号以内的句子全部定稿或失败，再等这些句子的定稿版本全部收到 `utterance_saved`。
4. 发送 `ask`，带上 `cut`。

**云端如何使用转录：**
- 对 `cut` 里列出的通道，只使用 `ordinal` 不为空、且不超过截止序号的句子，取最新版本。截止之后产生的句子，即使已经先入库，也不能用于这次回答。
- 其他已经关闭的通道，按原规则使用回答创建前一小时内的句子。
- 网页远程触发的回答，执行的是同一段代码。

**超时：** 不发出回答，沿用「不带缺失的上下文开始回答」的约定，并说明具体是哪种情况：
- OpenAI 没有确认最后一次提交；
- 最后一句还没有定稿；
- 最后一句转写失败（附 code）；提交被拒即使没有 item_id 或 ordinal，也不能当成截止成功；
- 最后一句还没有保存（附原因）；
- 与云端的连接已断开。

**停止：**
- 本机采集一停，就算停止成功。
- 随后强制提交一次；OpenAI 通道等截止范围内的句子定稿（最多约 10 秒）后关闭。
- 没保存的句子继续按确认机制重发。
- 尾句的状态单独提示，并说明具体原因。

**删除：** 停止结果里的 `complete`，以及所有「音频尾句未全部确认」的提示。

## 四、云端连接的 CPU 限额（待定）

- **事实：** Sites 对每个 WebSocket 请求累计计算 CPU，上限 32 秒。这是总量预算，不是时长限制。回答的流式转发是主要的消耗之一。
- **本节不是修复本次「旧图」和「保存卡死」的前提，先不实施。**
- **先测量：** 用一场真实会话的 `/capture/socket` 日志，计算 `cpuTimeMs / wallTimeMs`。
- **测量后再决定：** 如果按这个速度，常规面试时长内会碰到限额，再实施由电脑主动更换云端连接：
  - 挑没有回答在生成、也没有在等回答截止的时候换。
  - 新连接接管所有权，旧连接由电脑关闭；电脑把这次接管认作自己发起的交接，而不是「被其他客户端替换」。
  - OpenAI 通道不受影响；未确认的句子在新连接上重发。
  - 更换周期按实测留出余量，不预设 40 分钟。
- **前提：** 转录必须先归电脑负责，也就是第二节完成之后才能做到。在现在的设计里，转录挂在云端连接上，连接一关闭（`dispose`），转录就结束了。

## 五、错误记录

- **云端：** 去掉转录、保存、心跳、读取路径里吞掉错误的 `catch`。统一按 `audio.js` 末尾 `failure()` 的写法输出 JSON 日志，包含 `event`、`stage`、`code`、`name`、`message`（截断）。
- **电脑端：** 记录 OpenAI 的 error type、code 和内层 `event_id`，以及连接关闭码、提交超时、积压超时、保存失败原因。Mac 用系统日志，Windows 用现有的日志通道。
- 任何日志都不包含转录文字、截图内容、凭证或个人资料。

## 六、测试要求

- **清理现有测试：** 删除把错误行为写成规格的测试（`context.test.mjs:77-81`）。修好 `docs/releases/2026-10-18-transcription-persistence.md` 里记录的三个现有失败测试；修的方式是按本文的约定改测试，不是迁就代码。
- **模拟环境要能注入故障：**
  - OpenAI：带或不带内层 `event_id` 的 error、提交既不确认也不拒绝、连接关闭、事件格式异常。
  - D1：写库失败若干次后恢复；写入其实成功但返回了错误（结果未知）。
  - Cue 连接：中断与重连。
  - 可控的时钟。
- **必须成立的规则：**
  - 任一已签发的 cursor，或者不带 cursor：新图保存后，下一次读取一定附上它。新图最新，一定排在预算之内。
  - 回复丢失后重用同一 cursor：丢失那次的内容都不会被记为已送达。本次从新到旧在预算内返回，装不下的留在 `more` 里，之后用新 cursor 都能取到。
  - 原图读取失败时不写新 cursor。
  - `now` 和 `age_seconds` 随时钟变化。
  - 同一 cursor 并发读取都能成功。
  - cursor 无效或过期时，按首次读取处理，并带 `reset`。
  - 新图超过四张时，在字节预算内优先附最新原图（最多四张，不承诺固定四张），其余用新 cursor 在对应 more 模式中继续取得。
  - `structuredContent` 与文本块内容一致，两者合计不超过预算。
  - 写库连续失败后恢复：转录不中断，所有句子最终都保存成功，原因有日志。
  - 每一路最多一个未确认提交；被拒的提交按内层 `error.event_id` 结束；提交超时按断线处理；后续句子的序号不会错位。
  - 回答只使用截止范围内的句子：截止后产生的句子，即使先入库，也不进入这次回答。
  - 停止总是成功；尾句状态单独、具体地报告。
  - 心跳查询偶发异常时不断开；确认被接管或持续 30 秒无法确认所有权时断开。

## 七、不改的部分

- 截图采集、连拍、上传，以及由服务器确认的就绪状态。
- OpenAI 模型（`gpt-live-transcribe`）和断句参数。
- 音频不经过 Sites，两路不混音。
- 意外断线后需要手动重新开始转录。
- 不自动录音、不自动回答、不自动重试回答。
- MCP 保持只读，只有三个工具，不做 MCP Apps 或通知。
