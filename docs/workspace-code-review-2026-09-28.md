# 工作区改造后的代码审查

范围：本轮新增的方案发布、拆步、复杂度、同题历史、往场档案、阅读位置及其工具/界面衔接。没有将整个项目既有的未提交改动一并重构。

结论：核心职责划分可以继续使用。确实发现了重复的发布路径和不必要的隐式判断，已删除；同时修复两个状态关联问题。

## 已修复

1. **旧版扁平建议通道可以绕过拆步限制。** `update_code` 原先仍接受顶层 `changes` 直接发布，与新方案发布并存；拆步任务可以意外走旧通道替换整份建议。已删除旧发布实现，所有 propose 都经过同一套方案、文件和拆步验证。观察实际代码仍独立处理。
2. **步骤身份由标题和代码偷偷推断。** 相同标题和代码可能被自动认作旧步骤，与 schema 中“null 表示新步骤”的约定冲突。已删除猜测逻辑；保留明确 ID 才沿用原步骤。
3. **拆步清空了未变化的基线复杂度。** 原逻辑将任何 steps 提交都当成重建基线。现在拆步保留原基线复杂度，继续验证拆分前后最终代码相同。
4. **查看历史误用了写入版本检查。** 编辑器发生新观察后，旧页面发起的只读历史请求可能被拒绝。现在读取只按历史身份定位；修改操作继续严格核对当前题目与实际文件版本。
5. **提示词仍建议使用已不提供的手动保存入口。** 改为请求更清楚的截图，错误提示同步修正。

前三个可执行回归在修复前已复现失败（旧通道、拆步复杂度、只读历史）；补充了显式步骤身份测试。原协议回放改为使用当前分步输出约定，并在观察实际代码后重新读取上下文；没有放松版本保护来兼容旧测试。

## 保留的复杂度及理由

- 实际文件、建议快照、历史快照各有用途，不能合并成同一份可变代码。合并会重新引入“建议等于已写代码”的错误。
- 任务有效性与每个文件版本都要检查，分别防止取消/换题后的旧任务写入和观察更新后的旧 patch 覆盖。
- 分析/步骤独立更新和拆步末态验证是已确认的产品行为，不新增阶段分类器来代替。
- 界面阅读位置属于每个客户端；代码和方案事实仍由服务端保存。不能为了少几个状态变量把所有客户端的阅读位置同步成一个。
- 旧后端能力检测仍保留，防止连上不支持新操作的服务时误发控制。底层手动保存/撤销协议仍有既有约定和测试，本轮没有将它扩回产品界面。

未增加按钮、模型连接、题型/阶段状态机或第二套发布协议。未以“更通用”为由新增抽象层。
